Overview

MessApp is a React/Vite messaging client packaged for the web, Capacitor mobile, and Tauri desktop from one build. Supabase supplies authentication, Postgres access, Realtime signaling and presence, and Storage.

The browser owns UI state, optimistic message state, Web Crypto operations, and WebRTC media. Server authorization is enforced by deployed Row Level Security policies, Storage policies, and RPC grants.

Frontend visibility checks are never an authorization boundary. Role and permission checks in the UI exist to keep the interface honest; every operation must also be authorized by the deployed backend.

Frontend architecture

  • src/App.jsx initializes theme and native keyboard behavior, tracks the Supabase session, handles recovery and deep-link routing, and chooses between the auth screens and Dashboard.
  • src/components/Dashboard.jsx is the authenticated coordinator. It loads profile, DM and server navigation, presence, permission, modal, and voice-channel state.
  • src/hooks/useChatManager.js owns the active conversation's messages, pagination, optimistic sends, Realtime reconciliation, reactions, typing, attachments, and the encryption boundary.
  • src/hooks/useWebRTC.js owns one-to-one call signaling, peer and media state, and Android audio routing.
  • Layout components render parent-owned state. Modal components must not become alternative data authorities.

Styling is Tailwind v4 through the @tailwindcss/vite plugin: there is no tailwind.config.js and no postcss.config.js. The design system lives in src/style/index.css as an @theme block plus CSS custom properties redefined per theme and per surface tint.

vite.config.js sets base: './' so the same dist/ loads from Capacitor and Tauri file:// shells, and in production drops console and debugger through esbuild. Raw console.* calls therefore vanish from production builds; diagnostics route through src/lib/debug.js instead.

Supabase architecture

src/supabaseClient.js creates one browser client from VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY. The app reaches profiles, DMs, servers, channels, messages, reactions, reads, friendships, call state, and Storage through table queries and RPCs.

The migration chain starts from the pre-hardening Supabase baseline: extension helpers, the remote schema snapshot, Realtime publication membership, the Storage baseline, and the leave_server lint correction. Later migrations depend on that baseline and must stay in timestamp order. Rebuild only the disposable local stack with npx supabase db reset --local; never run db reset --linked, which targets hosted state.

The conversation-security delta removes permissive legacy policies, restricts direct membership and room creation, corrects channel membership checks, makes the chat-attachments bucket private, and scopes attachment access to authenticated conversation participants. Normal DM creation must use create_or_get_dm(peer_id) and server joins must use join_server_by_code rather than direct client inserts. A matching transactional isolation test verifies that participants reach their own conversation while an unrelated user cannot read, send, join, view attachments, or upload into it.

A passing frontend build is not proof that remote RLS is current. Authored migrations and deployed policies can drift. Database and Edge Function deployment is a separate, explicit, reviewed operation — never a side effect of unrelated work.

The whole supabase/ workspace — configuration, Edge Functions, migrations, tests, reference exports, and generated schema snapshots — is intentionally local-only and excluded from Git.

Authentication and session

  1. App asks Supabase Auth for the persisted session and subscribes to auth changes.
  2. Login, register, and recovery components call Supabase Auth and leave session ownership with App.
  3. Dashboard loads the authenticated profile and its dependent navigation data.
  4. Capacitor deep links return recovery and login callbacks to the browser route.
  5. Logout clears the Supabase session. Local privacy and key settings stay under explicit control of the settings flows.

Never log auth tokens, recovery fragments, passwords, push tokens, or private key material.

Messaging

useChatManager derives one active target from a DM room or a server channel. It loads cached and recent rows, decrypts content where applicable, and subscribes to target-scoped Realtime changes. Each open conversation subscribes to a room:<targetId> channel carrying both postgres_changes (messages, attachments, reactions, reads) and presence for typing.

Sends create a local optimistic row, perform the encryption, upload, and database work, then reconcile that local row with the matching server insert. A room switch must invalidate stale asynchronous work, reject results belonging to another target, and remove the old Realtime and presence channels before their results can touch the new room.

Pagination prepends older rows without disturbing newer optimistic or Realtime entries. The bounded local cache is an availability optimization, not authoritative state. Delivery and read markers derive from backend timestamps and current visibility.

Encryption

Direct messages are end-to-end encrypted with Web Crypto: ECDH-derived AES-GCM keys, private keys held in localStorage. Server channels are not encrypted. This is real cryptography but not a full ratcheting protocol — see Security boundaries.

Disappearing messages

Expiry rides on messages.expires_at, chosen per conversation from the composer's hold-to-open send options (src/lib/messageExpiry.js). The messages_read_participant policy is the enforcement point: an expired row stops being returned to anyone. The client-side sweep and cache filter only keep an already-open conversation from showing a row the server would no longer hand out. Rows are hidden, not reclaimed — public.delete_expired_messages() is a service_role entry point with no scheduler wired to it yet.

Push delivery

The push path is deliberately content-blind: providers receive conversation routing identifiers and a generic notice, never message plaintext, encrypted payloads, or attachment URLs.

  1. A signed-in installation opts in from user settings and registers its FCM or APNs token into push_devices under RLS.
  2. A database trigger calls the send-message-push Edge Function after a message insert, and after a pending friend-request insert.
  3. The function reloads the message and membership data with the service role, derives recipients from DM or server membership, excludes the sender, blocked users, and muted server members, and claims an idempotent delivery event.
  4. Devices that reported this conversation on screen within the last 90 seconds are dropped from the send, so a message you are already reading raises no notification. That report is written only while the app is visible and it expires, so a force-quit app cannot silence a chat.
  5. One bounded scan of the conversation plus the reader's own read marker becomes a per-recipient unread count, so a burst reads as "4 new messages" rather than four notifications. Providers collapse by conversation, so the newest notification replaces the visible one instead of stacking.
  6. Tapping a notification opens the target DM, server channel, or notifications tab after access is revalidated through the signed-in user's normal queries.

The webhook record supplies only the message identifier as trust input, and the function authenticates with a shared webhook secret rather than a user JWT, because database webhooks carry no session. Hosted setup — provider credentials, function secrets, webhook configuration, and credential rotation — is an operator task kept outside this repository.

Attachments and links

The chat hook maintains one composer attachment queue capped at 10 items. Images, GIFs, videos, and general files may be mixed in one outgoing message with one optional caption. Selection, paste, Android keyboard media, and GIF search all feed that same queue, and each item is validated before it enters. Images and videos get local previews, files show name, type, and size, and removing one item does not clear the rest.

On send, the hook validates type and size, encrypts DM attachment bytes where configured, uploads every item to the private chat-attachments bucket, creates one message, and inserts the matching message_attachments rows. Receiving clients resolve and decrypt each attachment independently, so one unavailable object does not hide the rest of the media.

Object paths use the uploader and conversation identifier as authorization inputs. Read paths resolve stored object paths to temporary signed URLs and decrypt bytes at the client boundary. Signed URLs, file contents, plaintext, and encrypted key material must never be persisted in diagnostics. The frontend may cache resolved media for performance, but access is ultimately controlled by deployed Storage policies and conversation membership.

Plain HTTP(S) links stay message content rather than Storage attachments. A message renders up to 10 distinct safe link previews; YouTube links use privacy-enhanced embeds and other URLs fall back to a safe clickable card when metadata lookup fails.

Reactions

Reaction replacement removes the current user's prior reaction before inserting the normalized new emoji. UI state updates only after the write succeeds, and the cache is updated consistently with it. Realtime message and reaction changes remain the cross-client source of convergence.

Servers and channels

Dashboard owns selected server and channel state and passes permission decisions down to the sidebar and settings modals. One-to-one rooms are created only through create_or_get_dm(peer_id), which derives the caller from auth.uid(), checks friendship, block, and privacy rules, serializes the user pair, and inserts both memberships atomically; the frontend navigates with the returned dm_rooms row.

Server creation, joining, and invites depend on backend RPCs. Categories, channels, and membership depend on RLS-protected writes. UI checks for owner, admin, and member roles are not substitutes for backend enforcement. Voice-channel switching must leave the previous media session before joining another.

Voice and WebRTC

useWebRTC implements DM call states from ringing through connecting and connected to terminal outcomes. It owns the peer connection, offer/answer and ICE exchange, local camera and microphone tracks, remote streams, timeout handling, and teardown. Tracks and senders must stop exactly once, signaling subscriptions must be removed, and late ICE or signaling must not revive an ended call. Call signaling travels on a separate global-signaling broadcast channel, unrelated to the per-room channel.

Group voice is a WebRTC mesh, not an SFU despite the SfuScreenShare component name: every participant holds a direct peer connection to every other participant. Dashboard and media-session state supply participants and streams; the component owns only view state — pin, grid, carousel, page, and watch selection. Stream identity should use stable participant and track identifiers rather than array position.

TURN credentials are minted short-lived by a Supabase Edge Function using coturn's HMAC time-limited REST scheme, and consumed through src/lib/iceServers.js. There is no built-in default relay. Without a configured TURN host and shared secret the function returns 503 and every call degrades to STUN-only, which connects only when both peers are directly reachable.

Screen sharing

Screen and camera tracks are upstream-owned media resources. SfuScreenShare binds them to video elements, chooses responsive layouts, and reports user actions upward. Pinning and stopping a watch change presentation and subscription intent; they do not transfer track ownership. Cleanup detaches element streams and leaves track shutdown to the layer that created them.

Native shells

Mobile and Capacitor

App configures body-resize keyboard behavior and the Android back and deep-link lifecycle. CSS safe-area and viewport variables keep composer trays, call overlays, and long-press portals above the keyboard and system UI.

Two authored Android bridges exist:

  • MessAppWebView and KeyboardImagePlugin accept images committed by Android keyboards, copy temporary URI content into app-private storage, and notify JavaScript.
  • CallAudioPlugin enters Android communication audio mode, switches speaker routing, and restores the pre-call audio state.

Temporary URI permissions, streams, plugin listeners, and audio routing all require cleanup. Generated Capacitor assets are not authored source.

Desktop and Tauri

src-tauri/src/main.rs starts the desktop shell and suppresses the extra Windows release console. src-tauri/src/lib.rs owns the Tauri lifecycle and enables native informational logging only in debug builds. The React application and the Supabase client stay shared with web and mobile.

Security boundaries

  • Supabase Auth establishes identity. RLS, RPC grants, and Storage policies establish authorization.
  • Web Crypto helpers handle ECDH, AES-GCM, fingerprints, randomness, and PIN wrapping. They do not provide a full ratcheting protocol and do not independently prove peer identity.
  • Rendering routes untrusted links and media through src/lib/security.js. Markdown must not bypass those checks.
  • Local caches and localStorage are device-local convenience state, not trusted backend truth.
  • Diagnostics must exclude tokens, passwords, private or encrypted keys, full message content, signed URLs, service-role keys, and attachment contents.

Repository hygiene

  • This page (docs/index.html) is the project-level system reference. It is the only documentation the repository publishes besides README.md; other markdown is ignored by Git and stays local.
  • Keep the entire supabase/ directory local-only. Its configuration, Edge Functions, migrations, tests, reference exports, generated schemas, and local state must never be staged or committed.
  • Keep database dumps, environment files, service-account material, signing keys, and local credential files out of Git. .env.example holds variable names and safe placeholders only.
  • Do not edit generated build directories. Android, iOS, and Tauri source projects are tracked; their build caches, local SDK paths, signing files, and platform service credentials are ignored.
  • Database deployment is a separate, explicit operation. Review the migration diff and run the local isolation checks before applying anything to a remote project.
  • Never commit, deploy, or push as a side effect of documentation or local validation work.
